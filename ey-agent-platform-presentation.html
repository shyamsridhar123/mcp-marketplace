Executive message

Build anywhere. Govern centrally. Package for reuse.

The cleanest articulation for EY is this: the hub registers MCPs, skills, and agents under EY policy, orchestrates their approved use, and packages governed capability for downstream applications.

  • It already contains the right nouns: integrations, skills, agents, blueprints, approvals, compliance, intelligence.
  • It already contains the right controls: Entra identity, DLP, audit traces, lifecycle states, Work IQ context.
  • It can govern even when the end-user experience lives somewhere else, including Copilot Studio or other integrated agent+UI platforms.

Target operating model

Build anywhere, govern centrally, consume safely

The architecture works best as four layers: experience surfaces, the EY governed platform plane, the MCP/runtime boundary, and the broader enterprise control plane.

Microsoft fit

How Agent 365, Copilot Studio, and AG-UI fit the EY story

These three concepts do different jobs. The deck is strongest when it keeps their responsibilities separate.

A

Agent 365

Microsoft positions Agent 365 as the enterprise control plane for agents across the organization, regardless of where they were built or acquired.

  • Registry and map for all agents
  • Access control aligned to Entra and enterprise security posture
  • Governance, observability, security, and interoperability at tenant scale
EY AI Agent Hub aligns naturally to this story as the business-facing governed registry and orchestration plane inside that wider control model.
C

Copilot Studio

Copilot Studio is a build, manage, and publish surface for agents, including scenarios that already have their own integrated end-user experience.

  • Low-code and managed authoring surface
  • Supports internal and external publishing paths
  • Does not require EY to own every end-user UI
If the UI already exists elsewhere, EY still adds value by governing MCP registration, approvals, packaging, telemetry, and allowed orchestration paths.
G

AG-UI

AG-UI is an open event-based agent-to-UI protocol covering run lifecycle, streaming messages, tool calls, and state synchronization.

  • Text and reasoning message events
  • Tool-call start, args, end, and result semantics
  • State snapshots and deltas for rich interactive UIs
This repo does not implement AG-UI today. It is the next interoperability layer EY can adopt to standardize multi-runtime front-end behavior.
Important honesty point: the current platform already aligns to Agent 365 concepts, but it should not claim AG-UI is already shipped. Position AG-UI as the interoperability layer EY can adopt on top of the existing governed hub.

Governance through the MCP tools layer

Even when the agent and UI are elsewhere, EY still owns the operating guardrails

This is the most important strategic clarification: if a solution such as Copilot Studio already has an integrated agent and UI, EY can still add governance and orchestration through the MCP layer.

UI

Scenario A — EY owns the downstream application

The app consumes a governed package from the hub instead of hand-wiring agents, tools, approvals, and telemetry every time.

Register: approved MCPs, skills, agents, and blueprints are cataloged once.
Govern: identity, DLP, audit, lifecycle, and compliance are attached before release.
Package: downstream teams get a reusable capability bundle, not a pile of infrastructure decisions.
MCP

Scenario B — Another platform owns the experience

The user experience may live in Copilot Studio, a partner product, or another integrated surface, but EY still governs what tools and behaviors are allowed.

Register: MCP capabilities are inventoried and approved centrally.
Orchestrate: policy, audit, and approvals are enforced at the tool-access layer.
Observe: traces, signals, and compliance posture flow back into EY’s governed operating plane.

Why this matters

EY does not need to win every UI to win the platform layer.

  • Govern the approved MCP estate once instead of rebuilding guardrails per solution.
  • Turn orchestration into policy-managed capability, not just prompt wiring.
  • Make downstream application teams faster by handing them approved packages with clear ownership and telemetry.
  • Stay compatible with Microsoft-native surfaces while still adding EY value on governance, packaging, and oversight.

Roadmap

Recommended next moves for EY

The goal is not to create another agent ecosystem from scratch. It is to use this platform as the governed productization layer over capabilities that may be built in multiple runtimes and consumed in multiple experiences.

Phase 1

Operationalize the registry

Use the current hub as the source of truth for integrations, skills, agents, identity, and approvals.

  • Treat Marketplace, Agents, and Governance as the authoritative inventory.
  • Formalize approval workflows for MCP registration and blueprint activation.
  • Attach ownership, lifecycle, and compliance metadata to every governed asset.
Phase 2

Productize packaging

Turn governed capabilities into consumable packages rather than one-off solutions.

  • Define package manifests for blueprint, skills, allowed MCPs, identity, and telemetry.
  • Make downstream consumption paths explicit for internal apps and embedded assistants.
  • Support reuse across EY apps, partner solutions, and Microsoft-native surfaces.
Phase 3

Add interoperability and policy automation

Standardize runtime contracts and automate enforcement at the MCP tools boundary.

  • Introduce AG-UI adapters where multi-runtime UI interoperability matters.
  • Enforce policy, audit, and DLP at MCP invocation boundaries.
  • Feed signals and traces into a repeatable enterprise operating model aligned to Agent 365.
Closing message
The winning story is not “we built another agent UI.” It is “we built the governed plane that lets EY safely register, orchestrate, and productize agent capability for every downstream experience.”
